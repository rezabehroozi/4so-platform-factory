# Agent repository instructions

This file is a machine-consumed contributor contract. It intentionally contains stable engineering rules, not release history or project-state mirrors.

## Minimal continuation path

For a fresh coding/test agent, do not reconstruct orchestration from source before checking the compact continuation capsule:

1. Run `make autopilot-context` first. It emits the hard-budget `AUTOPILOT_AGENT_CONTEXT_COMPACT_V1` packet only; use `make autopilot-context-full` solely for orchestration/debug diagnostics. The compact packet's `outerRuntime.action` is derived from canonical `project_runtime.py status` and tells you whether to observe a live wrapper, run `make runtime-resume`, resolve recovery, or continue normally.
2. Consume only `environmentPreflight.remediationHints`, `failurePathHints`, `ownerContextPaths`, `proofCommand`, `proofTimeoutSeconds`, `resumeInvocation`, `nextActionCode`, `nextCommand` and `nextAction` before broad repository search. Treat `nextActionCode`/`nextCommand` as the machine continuation contract; prose is explanatory only. The compact handoff is capped by `contextBudgetChars`; never replace it by dumping report/event logs into model context. If `contextFallbackAuthority=AUTOPILOT_CONTEXT_BUDGET_FALLBACK_V1`, arbitrary or inner oversized argv were intentionally omitted. Execute only the emitted `nextCommand`: it may preserve `make runtime-status` or an already-admitted fixed `make runtime-resume`; recovery-required and environment-remediation handoffs remain inspection/status-first, and every other oversized action falls back to status inspection. Never reconstruct an omitted command from prose.
3. If environment is blocked, repair only the named prerequisites and then execute the exact machine `nextCommand`. For an inner-only block this may be `resumeInvocation`; when `nextActionCode=REPAIR_ENVIRONMENT_AND_RESUME_OUTER_RUNTIME`, the compact packet intentionally drops the inner invocation and `nextCommand` is `make runtime-resume` so canonical project-runtime rejoins the same checkpoint. Never reconstruct an omitted command or edit product source for an environment blocker.
4. If a code/test failure exists, inspect the named failure-path hints and owner surface first. Run only `proofCommand` while diagnosing; final convergence can repair a newly discovered owner defect inside the same bounded campaign.
5. Execute only the command admitted by `nextActionCode`/`nextCommand`. `RESOLVE_OUTER_RUNTIME_RECOVERY` is inspection-only and must never be converted into replay; `OBSERVE_OUTER_RUNTIME` must not start a duplicate agent. `INSPECT_AUTOPILOT_STATE` means run only `make autopilot-status`; never reconstruct a missing resume command. Use `make autopilot-agent` only for `START_AUTOPILOT_AGENT`.

Bootstrap Installer continuation is similarly status-first: humans may use `bash install.sh start`, while coding/test agents should prefer `bash install.sh start --compact` so `INSTALLER_MANUAL_DOCTOR_COMPACT_V1` supplies only `doctorOutcome`, `actionable`, `blockerCodes`, `nextActionCode` and the exact non-secret `nextCommand`; use full Doctor only when human remediation detail is actually needed. Then follow `INSTALLER_MANUAL_MACHINE_NEXT_ACTION_V1` through prepare-bundle/preflight/plan/install and do not reconstruct custom flags. `INSTALLER_MANUAL_DOCTOR_ACTION_OUTCOME_V1` distinguishes `READY`, `ACTION_REQUIRED` and `BLOCKED`: `ACTION_REQUIRED` with `PREPARE_BUNDLE` is a normal canonical preparation handoff, not a product/code failure and must not trigger repair triage. For `BLOCKED`, consume only `blockerCodes` plus the matching `INSTALLER_MANUAL_DOCTOR_REMEDIATION_V1` `remediation.*` hints; do not broad-scan source, guess package-manager commands, or classify host/input absence as a code defect. `--out-spec` is intentionally not replayed, and a RUN_INSTALL continuation carries explicit execution plus DEPLOY confirmation only after plan review. After any disconnect/reboot use `sudo bash install.sh next` first: `INSTALLER_MANUAL_CONTINUATION_RESOLVER_V1` reads the host journal and routes to Bootstrap readback, explicit host recovery, staged verification, or a fresh Doctor path without automatic mutation. Bootstrap `run-status` then exposes `INSTALLER_BOOTSTRAP_MACHINE_NEXT_ACTION_V1` plus an exact non-secret `nextCommand` for safe CLI continuations. Human `nextAction` is explanatory only; never infer replay from raw state.

- Conversation/UI streams are observers/controllers, never execution authority. For coding/test continuation, read durable outer-runtime plus inner Autopilot state through `make autopilot-context` first; it calls the canonical project-runtime status path and must prevent duplicate starts while a live wrapper exists. For other long build/test/install/repair work, use `python3 scripts/project_runtime.py status` / durable Make targets directly. For coding/test agents, prefer the single `make autopilot-agent` execution entrypoint: it performs prerequisite checking, durable checkpoint/resume, compact failure handoff, read-only triage, bounded single-writer repair and owner-scoped convergence. Repair-agent capability is lazy under `AUTOPILOT_LAZY_REPAIR_CAPABILITY_V1`: a clean deterministic campaign must not require Codex before tests run; if a real failure occurs, triage/repair availability is checked fail-closed at that exact durable cursor. On a valid full-run resume, `AUTOPILOT_RESUME_PREFLIGHT_CURSOR_V1` scopes continuation to the remaining forward/convergence cursor, and `AUTOPILOT_PROGRESSIVE_STAGE_PREFLIGHT_V1` checks prerequisites at each exact stage instead of blocking early owner proofs on late-stage browser/build dependencies. Do not reinstall or investigate toolchains that belong only to already-green or not-yet-reached stages; fix only the prerequisite named at the blocked cursor and resume. A live recorded child is rejoin/observe-only and must not be blocked by unrelated browser/build/Codex prerequisites. Agent mode defaults to eight independent repair opportunities, while repeated same-stage/same-fingerprint failure still stops as `NO_PROGRESS` before another repair is spent; do not raise the budget to hide a loop. Under `AUTOPILOT_REPAIR_BUDGET_ACTUAL_WRITER_V1`, only a real workspace-write repair worker consumes `repairCount` or arms same-fingerprint `NO_PROGRESS`; read-only triage, environment/supply-chain classification, missing Codex and browser-triage prerequisites preserve the durable cursor without burning repair budget. Before broad repository reading, use `make autopilot-context` and inspect its bounded `failurePathHints` first, then the named owner-path set and exact proof command. `AUTOPILOT_LOW_TOKEN_CONTEXT_V2` keeps the normal continuation packet within 4800 serialized characters; do not call `make autopilot-context-full` unless the compact packet is structurally incomplete or orchestration itself is the suspected defect. Unambiguous missing-executable/permission and required Playwright/YAML module failures are classified by `AUTOPILOT_DETERMINISTIC_ENV_TRIAGE_V1` before model triage; fix only the named host prerequisite. The workspace-write repair worker must not rerun the failing stage, broad suite, build or release verifier: `AUTOPILOT_REPAIR_PROOF_DEDUP_V1` makes the controller own the exact post-repair proof and final convergence. Exact same-stage/same-fingerprint triage is cached durably, so after crash/resume do not ask another agent to reclassify the same failure; rerun the admitted continuation and let Autopilot reuse the bounded triage capsule. If a separate coding agent applies the reported `CODE_DEFECT` directly to the working tree, rerun `make autopilot-agent`: Autopilot may adopt that patch at the existing checkpoint only when Git HEAD/report/graph/failing-stage still match and every changed file is inside that owner surface. Cross-owner changes, Git commits, or edits to Autopilot/validation orchestration deliberately reset the checkpoint rather than reusing stale green proofs. Start other interactive heavy work through `scripts/project_runtime.py`/the durable Make targets so run-id, PID identity, Git HEAD/origin-main, heartbeat, checkpoint and disk log survive observer disconnects. C6 Autopilot repair wrappers alone opt into `PROJECT_RUNTIME_OWNED_WORKTREE_MUTATION_V1`: the outer runtime keeps exact pre-execution source binding and immutable HEAD/branch identity, while allowing the inner Autopilot owner to repair and rebind only the working-tree fingerprint. Release/Physical wrappers never opt in. A terminal outer run with `replaySafe=true` must continue through `RESUME_OUTER_RUNTIME` / `make runtime-resume` even when `safeToRetry=false`; do not attempt a duplicate start merely to discover `RESUME_REQUIRED`. If the inner Autopilot report is `ENVIRONMENT_BLOCKED`, repair its bounded prerequisites first and use `REPAIR_ENVIRONMENT_AND_RESUME_OUTER_RUNTIME`; blind outer replay before remediation is forbidden.
- Durable runtime state and the single-writer lock are local runtime artifacts and MUST NOT be committed. A RUNNING state with a disproven PID identity is an interrupted/orphaned run, not success. The watchdog may reclaim a lock only after PID/start-time validation proves the owner dead and no tracked child remains. Destructive/physical runs are non-replay-safe by default: after interruption, inspect authoritative product/installer state before replay.
- Product behavior is authoritative in implementation, schemas, migrations and tests. Do not create prose source-of-truth layers for runtime state.
- Production control-plane state must be durable; do not introduce an implicit in-memory production fallback.
- Preserve fail-closed handling at authoritative persistence, approval, credential, rollback/recovery and supply-chain boundaries.
- Raw secrets must not be persisted in API resources, audit/event payloads, generated artifacts or Git. Use the existing credential-reference and secret-injection boundaries.
- Agent bootstrap bearer enrollment is one-shot; certificate rotation/re-enrollment must use the certificate authority workflow.
- Resolved catalog sources must remain exact, offline-verifiable and digest-bound. Helm sources must also retain exact render-generation provenance (toolchain, render semantics and values-file digests). Do not convert an unresolved research source into executable state by setting flags or placeholder digests.
- Local/unit/smoke success is not external runtime certification. Never promote a local result into an external/production claim.
- The deterministic Lab runner owns test execution and PASS/FAIL. AI diagnosis and MCP read tools are advisory/read-only; `mcp.operate` may invoke only allow-listed product mutations through normal RBAC/project/revision/approval/durable-audit authority. AI/MCP can never infer Physical PASS. Any AI/agent repair changes the source/artifact identity and requires certification to restart from M00 on the new exact SHA.
- Runtime certification scope must match what the run actually installed and verified from immutable source. Target/cluster capability evidence must not be reused as per-component certification for components that were not installed by that run, and source/offline plan metadata must never become execution-ready without durable control-plane certification authority.
- Add regression coverage to the existing owner package or smoke suite. Do not create release-numbered validators or require validator churn merely because a version/source file changed. Do not manually rerun the full test graph after each agent patch: rerun the failing owner proof, then let Autopilot select owner-scoped final convergence from the repaired stage and dirty delta; full convergence is reserved for cross-owner/ambiguous changes.
- Operator Console and Bootstrap Installer changes must follow `DESIGN.md`, the canonical product design language. Preserve workflow clarity, runtime truth, accessibility, responsive behavior and the anti-generic enterprise UI constraints documented there. For manual Bootstrap Installer work, start with `bash install.sh start` and after interruption resume orientation with `sudo bash install.sh next`; do not bypass the packaged `install.sh`/`platformctl installer-manual` owner path with ad-hoc systemd or shell mutation. Doctor must be green for host OS/architecture plus exact-release binary runtime/version before preflight; a Doctor `ACTION_REQUIRED/PREPARE_BUNDLE` outcome is also healthy continuation state and means run its exact preparation command, not repair source. After host deployment, use the same entrypoint for host `status`/`verify`, live `bootstrap-status`, explicit `resume --confirmation RESUME`, journaled `reset --confirmation RESET`, `reset-resume --confirmation RESUME-RESET`, host `recover` and `rollback`; `bootstrap-status` owns the stable machine-readable `nextActionCode` plus the state-specific human next action and every Bootstrap mutation must read durable Installer status first, derive confirmation from the exact durable run identity where required, and must never blindly replay a lost-response mutation. Local sudo is required for the canonical private `/var/lib/4so-platform-installer/bootstrap-token`; an explicit readable custom token file or injected token may be used for remote/custom continuation without unrelated local root privilege.
- Keep documentation minimal and current. Git is history; do not add handoff/state/roadmap/audit Markdown mirrors.
- Derived agent knowledge, OpenWiki-style claims, Archify-style diagrams and search indexes are discardable projections, not authority. Prefer `platformctl target-architecture` plus `scripts/generate_agent_knowledge.py`; never hand-edit generated knowledge into a parallel architecture/roadmap truth.
- Browser-agent diagnosis is developer tooling only. The canonical optional Chrome DevTools MCP profile is emitted by `scripts/browser_triage_profile.py`. Before browser-agent repair, `scripts/browser_triage_bootstrap.py --ensure` must verify/provision Node/npm/npx plus supported Google Chrome/Chrome for Testing on Windows/Linux; do not treat arbitrary Chromium as guaranteed MCP support. Use isolated disposable browser state with telemetry/CrUX/update checks disabled and never expose production credentials. Playwright remains the deterministic UI gate.
- Persian UI changes must follow the pinned `third_party/persian-writing/SKILL.md` formal-but-human register and pass both `scripts/persian_ui_lint.py` and `scripts/persian_writing_gate.py`. VibeFarsi (`persian-rtl-ui`, `persian-ui-copy`, `persian-typography`) is an external design-research reference for Console work: use document-level RTL, logical inline/block CSS, zero Persian letter-spacing, Persian display digits/Jalali user-facing dates, LTR isolation for technical identifiers, semantic theme tokens, a 4px spacing grid and 44px interaction targets. Preserve the product-owned `webconsole/persian_glossary.json` terminology. Do not import VibeFarsi React/Tailwind runtime, source files, MCP availability, remote fonts or assets into the shipped product; 4SO owns the implementation and deterministic gates.
- When a stale validator conflicts with correct product behavior, fix the validator. When a test exposes a real product defect, fix the product owner layer rather than weakening the test.
- Local repository state plus `.project-runtime`/Autopilot checkpoints are execution authority. Git/GitHub is version-control/publication authority only; GitHub Actions, remote CI and external runners are never assumed to have executed a test. Autopilot triage/repair agents edit only the working tree and MUST NOT commit, push, reset, checkout, stash, rebase, merge or otherwise mutate Git history. A supervising caller may publish to the canonical repository/branch only when that caller explicitly authorizes publication, and any such publication must be atomic/read-back verified.
- Canonical repository: `https://github.com/rezabehroozi/4so-platform-factory`; canonical product branch is `main`. Do not create branch-specific execution truth or assume a conversational branch name. The canonical repository must contain every source/config/schema/migration/installer/deployment/test/validator/documentation/agent instruction needed for a new agent to continue from clone alone.
- Do not commit secrets, real `.env`, credentials/private keys, caches, runtime state, logs, generated smoke screenshots, local binaries or release build directories. If an essential large/third-party input is intentionally not ordinary Git source, document whether it is vendored, LFS, a submodule, or digest-locked installer/bootstrap acquisition.
